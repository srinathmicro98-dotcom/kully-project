Infrastructure reference — last updated 2026-09-12

How Kully is actually built

Kully is a multi-agent AI cofounder — text chat today, voice later — that you talk to from your phone or laptop. It remembers your projects, routes each message to the right specialist, starts and stops its own server to stay cheap, and can now write and run real code in a sandbox on your behalf. This is the map of every piece, why it's the piece we picked, and how they talk to each other.

01What Kully is

Everything routes through one idea: keep the always-on surface tiny and free, and let the expensive part sleep. A single Lambda function is the only thing running around the clock — it holds the login page, the "Connect" button, and nothing else. The actual brain — the chat orchestrator with your projects, your memory, your agents — lives on one small EC2 box that's off by default and wakes up on demand, then puts itself back to sleep after an hour of silence.

That single design decision is why nearly every other choice in this document exists: two AWS regions, a shared-secret handshake between two services that never fully trust each other, and a push-notification feature that's honest about its own limits instead of pretending to be more reliable than it is.

02System map

Two halves that barely know about each other on purpose: an always-on control plane (green) that only ever holds a login page and three buttons, and an on-demand chat plane (blue) that does all the real thinking — plus a sandbox (amber) the chat plane can reach into but that can't reach anything else.

03A request, start to finish

What actually happens between tapping "Connect" on your phone and Kully answering you.

Sign in, from a page that's always there

You open the Lambda's URL — not the chat server's, that one may well be switched off right now. It checks your username against a bcrypt hash and hands back a 30-day JWT.

Tap Connect

The Lambda calls ec2:StartInstances on your box and returns immediately. Your screen shows a "waking up your server" banner.

The box boots, on its own

Ubuntu comes up, systemd starts Caddy and the Node app automatically (no one has to SSH in). The browser polls /health every few seconds — usually ready inside 10–20 seconds.

You send a message

It goes to the EC2 box directly, bearing the same JWT the Lambda issued. A tiny classifier call to Groq decides: dev, general, or search.

The right specialist answers

That agent pulls in relevant long-term facts (Cohere embeddings + Supabase's pgvector), fresh web results (Tavily) if it's the search agent, or reaches for the code sandbox if it's the dev agent — then calls Groq for the reply.

The conversation remembers itself

The exchange is saved to Supabase, a quick Groq pass extracts anything worth remembering long-term, and it's embedded and stored for next time — even in a brand new conversation.

Left alone, it puts itself to bed

Every five minutes, EventBridge asks the box "how long since your last real request?" via a shared-secret endpoint. Past an hour of nothing, it calls ec2:StopInstances itself.

04Every piece, and why

Nothing here was the only option — each row is a real trade-off that got made on purpose.

Frontend PWA

web/ — vanilla HTML/CSS/JS, no framework
Why no framework
Three screens (login, chat, two panels) don't need React's bundle size on a box that also has to leave RAM for the actual product.
Why a PWA, not an APK
A native app's real payoff (mic access, push reliability) only lands once voice exists. Until then, "Add to Home Screen" gets 90% of the feel for 0% of the Expo/EAS build pipeline.
Served from
The control-plane Lambda itself — the page has to load even when the chat server is asleep.

Control plane

lambda/control-plane — Node 22, Lambda Function URL
Why Lambda
It has to be on 24/7 for the login screen to exist at all, and at this traffic level it's inside the always-free tier — an EC2 box for this alone would defeat the whole point.
Why a different region
ap-south-2 (where the EC2 box lives) doesn't support Function URLs yet, so this runs in ap-south-1 and just points its EC2 client at the other region explicitly.
Owns
Login, start/stop/status, push subscriptions, the idle-check schedule.

Chat orchestrator

server/ — Node 22 + Express, on EC2 t3.micro
Why Node over Python/FastAPI
Lower baseline RSS on a 1GB box, and the workload is 100% waiting on other people's APIs — an event loop suits that better than worker processes.
Why a real VM, not another Lambda
It needs to stay warm for a whole conversation's back-and-forth without cold-start tax each message, and systemd gives free crash recovery.
Stateless by design
Everything lives in Supabase — the process can restart, or one day run on more than one box, without losing anything.

Router + three agents

server/src/orchestrator/agents
How routing works
A cheap Groq call (gpt-oss-20b) reads the message and answers with one word: dev, general, or search.
Why editable prompts
Each agent's system prompt now lives in Supabase (agent_config, 60s cache) instead of only in source — you can retune a specialist's personality from the Skills panel without a redeploy.

Groq

the brain — chat completions
Why Groq
Free-tier LLM access that's genuinely fast, no self-hosted GPU to babysit on a t3.micro.
The catch
Its whole model catalog turned over mid-build (Llama 3.x retired) for gpt-oss reasoning models, which spend hidden tokens "thinking" before answering — every call now sets reasoning_format: hidden and budgets extra tokens for it.

Supabase

memory — Postgres + pgvector
Why Supabase
Managed Postgres with vector search built in, on a free tier, instead of self-hosting a database on the same tiny box that also runs the app.
Holds
Conversations & messages, long-term facts with embeddings, agent prompts, push subscriptions, routing logs.

Cohere

embeddings — embed-english-v3.0
Why a second AI vendor
Groq has no embeddings endpoint at all — this is the one gap Groq's free tier can't fill.
Used for
Turning extracted facts into 1024-dim vectors so a brand-new conversation can still recall something you said days ago.

Tavily

live web search
Why
Neither Groq nor Supabase can see the live web — Tavily is built specifically for feeding LLM agents clean search results.
Used by
The search agent only, injected as context before its Groq call.

05Identity & the secrets story

Auth and credential-handling weren't an afterthought bolted on — the account itself got tightened up before any of the app was built.

account

The AWS root access key was pasted into chat once — treated as burned on the spot. A scoped IAM user (kully-project) replaced it for all further work.

roles

Three separate IAM roles now exist, each able to do less than the last: kully-lambda-role (start/stop/describe one EC2 instance), kully-code-runner-role (touch one S3 bucket, nothing else), and the account-level user above.

login

Single user, no signup route exists anywhere in the codebase. A bcrypt hash lives only in the Lambda's environment — never in git, never in a chat transcript that gets persisted.

sessions

A 30-day JWT, signed with a secret shared between the Lambda (issuer) and the EC2 app (verifier only — it never issues tokens itself).

machine-to-machine

The EC2 box, the Lambda, and the code-runner sandbox don't share one master key — each pair that needs to trust each other gets its own shared secret (INTERNAL_API_SECRET, CODE_RUNNER_SECRET) with exactly one job.

06The sandboxed coding agent

The one piece with real teeth: the dev agent can now write and execute actual code, not just talk about it. Where that code runs was the whole design question.

The EC2 box holds the production secrets — Supabase's service key, three API keys, the JWT secret. Letting an LLM run arbitrary code there would mean one prompt-injected instruction away from those secrets. So execution never happens on that box at all.

Instead, Groq's native tool-calling (confirmed working on openai/gpt-oss-120b) lets the model decide when to call run_code. That call leaves the EC2 process entirely and hits one of two dedicated Lambdas — kully-code-runner-node or kully-code-runner-python — each running under kully-code-runner-role, an IAM role that can reach exactly one S3 bucket and nothing else in the account. Every invocation downloads that user's folder from S3, runs the snippet with a 10-second hard timeout, uploads whatever changed, and returns stdout/stderr. A file written in one message is still there in the next — proven live: a chat turn wrote project_note.txt, the next turn in the same conversation read it back byte-for-byte.

10Field notes & gotchas

The five things that didn't work the first time, kept here so they don't get rediscovered the hard way.

Groq's model catalog turned over mid-build

Llama 3.x disappeared from Groq entirely; the replacement gpt-oss models spend hidden reasoning tokens that can eat an entire small token budget before producing visible output. Fix: reasoning_format: hidden everywhere, plus real token headroom on short structured calls (routing, fact extraction).

A public Lambda Function URL needs two permission grants

Since October 2025, AWS requires both lambda:InvokeFunctionUrl and lambda:InvokeFunction resource-policy statements for anonymous access — the older one-permission pattern now silently 403s.

ap-south-2 has no Function URL support

Found this only by trying — the control-plane and code-runner Lambdas all live in ap-south-1 instead, with the EC2 client region pinned explicitly since it no longer matches the Lambda's own region.

Caddy doesn't auto-discover new routes

Every new backend route (/auth/*, then later /conversations*, /agents*) needs its own explicit handle block in the Caddyfile — forgotten twice, caught both times by a 404 that looked like a backend bug.

An ID selector can silently defeat [hidden]

#login-screen { display: flex } outranked the browser's default [hidden] { display: none } rule, so toggling .hidden in JS updated the DOM correctly while the screen stayed visually stuck. Fixed with an explicit #login-screen[hidden] { display: none }.

11What's not built yet

Voice

deliberately deferred
Plan
Groq's hosted Whisper for speech-to-text, Amazon Polly for text-to-speech — both are external API calls, so the 1GB box never has to run a model itself.

Native app, reconsidered

on hold, tied to voice
Why it's parked
An APK's real advantage — microphone access — only matters once voice exists. Revisit then, not before.

Tighter IAM

known, not yet done
Open item
The kully-project account-level user still holds AdministratorAccess rather than the recommended PowerUserAccess.

Kubernetes

the long-term scaling path
Why not yet
One box, started on demand, comfortably serves one user — k3s starts earning its keep once there's more than one workload or one user.
